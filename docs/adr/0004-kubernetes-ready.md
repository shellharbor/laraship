# ADR-0004: Kubernetes-ready Docker-архитектура

- Дата: 2026-10-02
- Статус: принято как архитектурное требование

## Контекст

Пользователь потребовал Kubernetes-ready для всей Docker-архитектуры: Docker Compose, микросервисов и Dockerfile. LaraShip сейчас разворачивает приложения через Bash и Docker Compose; предыдущие Docker E2E подтверждают этот способ запуска, а готовность текущей архитектуры к Kubernetes не проверена.

## Варианты

- Сохранить ориентацию исключительно на Compose — не выполняет новый запрос.
- Сделать переносимость образов и сервисов обязательным критерием, сохранив Compose как поддерживаемый слой развёртывания.
- Сразу заменить способ деплоя на Kubernetes — отдельное изменение реализации, выходящее за запрос на правила для агентов.

## Решение

Принят второй вариант: все образы, сервисы и генерируемые конфигурации должны удовлетворять [ai-kit/DOCKER.md](../../ai-kit/DOCKER.md). Compose-настройки хоста отделяются от runtime-контрактов; для компонентов определяются Kubernetes workloads, конфигурация, storage, probes, остановка и работа с репликами. Все агенты получают требование через [AGENTS.md](../../AGENTS.md), инженерный цикл и профиль project-continuity.

## Последствия

Новые Docker-изменения оцениваются также на переносимость в Kubernetes. Существующие несоответствия нужно выявлять и устранять в связанных задачах; принятие правила не подтверждает их отсутствие. Миграция кода, данных и способа развёртывания требует собственного плана и подходящих проверок. Текущие Compose-шаблоны и runtime в этой задаче не меняются.

## Проверка

Для этой задачи: согласованность правила в Core/профиле, валидность skill и локальных ссылок. Для реализации: проверки образов, lifecycle/state/replicas и, при добавлении Kubernetes-развёртывания, валидация manifests/Helm и проверка в изолированном кластере по [стандарту](../../ai-kit/DOCKER.md#проверка-и-review).
